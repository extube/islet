islet — run opencode, pi & hermes on your private AI-agent island in Docker

A free, open-source mini CLI app that runs AI agent harnesses in isolated Docker containers. One island per agent: opencode, pi and hermes coexist side by side — separate configs, persistent sessions, zero conflicts.

🧩 3 agents side by side 🐳 Docker-isolated 💾 sessions & libs persisted ⌨️ one binary: islet

Installation — how to install islet

# One-shot install: checks jq/docker, creates the config,
# and installs the "islet" command into ~/.local/bin
curl -fsSL https://raw.githubusercontent.com/extube/islet/main/install.sh | sh

# if you already have the repo:
./install.sh
The installer only asks for the config folder (default ~/.config/islet, override with ISLET_CONFIG_DIR), checks jq and docker, and puts the islet command on your PATH.

Why islet is good for running opencode, pi and hermes together

🧩

One config, many agents

Every agent gets its own entry in config.json: its image, its volumes, its network. opencode stays opencode, pi stays pi, hermes stays hermes — and each has exactly its own dependencies baked into its image.

↔️

Zero conflicts

Agents never see each other's config, sessions or installed libraries: config at ~/.config/<agent>, sessions at ~/.local/share/islet/<agent>-sessions, apk libs cache at ~/.local/share/islet/<agent>-libs. Update one — the others are untouched.

🔋

Survives restarts

Containers are ephemeral (--rm); everything valuable lives on the host: agent config, saved sessions/auth, the installed-libs cache. Restart or refresh Docker and you continue right where you left off.

🛠️

Same command for everyone

islet opencode ~/project, islet pi ~/project, islet hermes ~/project — the same interface for every harness: the agent runs in your directory under /workspace with a TTY, removed automatically on exit.

🎛️

Isolated network & env

host or bridge network with published ports and an env-variables map (API_KEY etc.) per agent — e.g. hermes gets its key, opencode gets a different one, and they never overlap.

🌊

3 commands to a new island

islet create → Dockerfile (with a choice of agent + preinstall environment), islet build → the image, islet setup → the entry in config.json. That's it:

Why run an agent in a container — the security side

An AI agent is an autonomous shell executor: it writes and runs code that no human fully reviewed, guided by a model that can follow prompt-injection instructions from raw files. That belongs behind a wall.

🚧

Only your workspace exists

The agent mounts exactly one host directory at /workspace. It can't see your documents, your browser profile, SSH keys — only what you handed over.

💣

Dangerous commands become harmless

rm -rf, broken curl | sh scripts, experiments with dd — they all happen on an ephemeral container filesystem that is removed on exit. The worst case is a rebuild, not a destroyed machine.

🧬

Prompt injection containment

Agents read a lot: README files, web pages, issues, code. A malicious file can try to steer the agent into leaking data. Inside a container, its total filesystem footprint is what you mounted — nothing more.

🔑

Secrets, scoped per agent

API keys pass in via per-agent environment maps and are stored in that agent's mount points. Your shell history, ~/.ssh, ~/.aws and global env vars are never inside the container.

🌊

Network you control

bridge mode with explicit published ports keeps the container off your host network; host mode is an opt-in, per agent. A runaway download or server can't touch your LAN silently.

🧾

Small, auditable surface

Each agent island is built from a Dockerfile you can read in one screen: Alpine base, a fixed package list, one installer. No opaque "autoconfigured" runtime, no leftover state from previous runs.

Still practice good hygiene: run docker as root/sudo is expected (islet calls the docker CLI), revisit what's published, and treat any agent — however helpful — as an untrusted program that writes code. islet just makes the blast radius a round corner of the internet: an island. 🏝️

Getting started — create, build, setup, run in Docker

# 1. create a Dockerfile (choose the agent + preinstall env)
islet create ~/my-agents/opencode.Dockerfile

# 2. build it -> image: islet/opencode:latest
islet build ~/my-agents/opencode.Dockerfile

# 3. register the agent in config.json (5-step wizard)
islet setup

# 4. run — both agents, two different projects, right away:
islet opencode ~/project &
islet pi ~/other-project &
islet hermes ~/third-project &

# list running agents / remove one / uninstall
islet ps
islet rm opencode
islet rm
